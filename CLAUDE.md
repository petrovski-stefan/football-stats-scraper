# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Selenium + BeautifulSoup scraper that collects finished football match data (teams, date, round, standings positions, HT/FT goals) from **nowgoal26.com** league pages, validates it with a Pydantic `Match` model (`domain/match.py`), and writes per-league CSVs to `data/raw/`. Purpose: analytics for two betting markets — comebacks (`is_comeback`) and over 6.5 goals (`is_seven_or_more_goals`). Package manager is **uv**; requires **Python 3.13** (pinned in `.python-version`).

Never call the site's data/API endpoints directly — always render pages in Selenium and parse the DOM.

**Before working on prediction, features, or analysis, read `notes/HANDOFF.md`** — the project's strategy/statistics guide: measured base rates, leakage traps specific to this pipeline, methodology rules, and the prioritized roadmap. Its companion **`notes/STATS_PRIMER.md`** explains the statistical tools the roadmap relies on (Empirical Bayes shrinkage, Brier scores, calibration curves, Dixon–Coles) with formulas and worked examples from this dataset. **`notes/ESOTERIC_MODELS.md`** holds seven further tools (Shin's method, favorite–longshot bias, Markov absorption, lead-survival hazards, state-space ratings, Pythagorean expectation, Kelly-as-KL) each tagged with the future moment to reach for it. **`notes/LEAGUE_STUDY.md`** reports the 23,127-match football-data.co.uk study (22 divisions across 11 countries — about one fifth of Europe, 2023-26) whose measurements supersede the older PL-only numbers — read it before designing any comeback feature: league/team comeback-proneness and the balanced-match precondition are refuted within the surveyed fifth, the trailing-team completion curve is measured, and the preregistered bar for admitting any of Europe's remaining ~30 countries as a comeback-candidate league is defined there. **`notes/RESULTS.md`** records the July 2026 attempt to overturn F12 using nowgoal-exclusive features (rolling HT-state history, 2H supremacy, corner-vs-goal pressure, site strength/crowd consensus, cross-competition congestion, venue/H2H splits) — all six families died, and the well-powered finding is that the *half-time state itself* is barely predictable: the bookmaker's price improves on a constant by only 0.64%. Read it before proposing any new pre-match comeback feature. Its **`notes/PREREGISTRATION.md`** is the template for how a claim in this project gets tested (closed family list, Holm correction, one holdout opening, amendments logged with dates). **`notes/FILTER_RESULTS.md`** then tested the opposite-signed question — can matches where a comeback is *impossible* be filtered out pre-match? — and that failed too: an oracle knowing the goal total excludes 44.2% of matches with zero misses, but the pre-match goal forecast reaches only AUC 0.559, recovering ~15% of the distance the bar needs. Both failures share one root: **pre-match forecastable structure in football is very thin**, and comebacks sit downstream of two weak signals (half-time state and goal total). Do not propose a new pre-match comeback feature without reading both. The reusable asset from that study is **`modelling/scoreline.py`**, a calibrated generative model of the full scoreline distribution — the natural instrument for the over-6.5 market (F9/F13), which is a direct functional of the same goal distribution. **`notes/MARKET_LINE_FINDINGS.md`** then measured what beat all of it: the bookmaker's Over/Under 2.5 line reaches AUC 0.592 on the comeback-environment conjunction where in-house features reached 0.497, and a two-column market model clears `PLAN_2026-07-25`'s top-20% slate bar out-of-sample at 1.33× (Wilson LB 5.68% vs 5.16% base, n=7,675). It is **exploratory, not preregistered** — read its §4 before quoting the number, and its §7 for why the corpus scrape's purpose changed. The football-data.co.uk corpus it was measured on was retired from the repo on 2026-07-26; §5 records how to re-fetch it. Finally, **`notes/BEHAVIOURAL_RESULTS.md`** records the 2026-08-29 test of a hand-weighted, frozen *candidate* rule (recovery/collapse/half-split/goal-volume profiles over each side's last 5 matches + 3 H2H): top-100 slate, 5 hits, 4.90%, **lift 0.88×** — the bar excluded at every slate size ≥ 50, because the score correlates +0.004 with HT-decisive and +0.006 with total goals. Two things there are load-bearing for any future work: the **candidate protocol** it introduced (judge a rule by precision@top-N with a Wilson CI and lift, never by AUC or Brier — a 3.6× rule scores AUC 0.527), and its cheap pre-test **screen every candidate rule outcome-free against the market price first**, since a rule orthogonal to the market is orthogonal to the best known signal. Finally, **`notes/RETRY_CANDIDATES_2026-09-23.md` is the closed 14-claim list for the upcoming multi-country scrape** — fixed before the data arrives, because best-of-50 selection clears the top-100 slate bar under a pure null. Read it before retrying anything that already failed. Two decisions there bind new work: **stratify by league, never test per league** (a per-league slate resolves only a 2.52× lift, while Mantel–Haenszel over league-season strata costs 2.9% SE and removes a real downward bias), and **F1 was moved out of the graveyard** — the EPL/Ekstraklasa gap is not goal environment but the completion rate conditional on HT-decisive (10.73% vs 6.85%, p=0.017), a quantity F1 never tested per league.

## Required runtime setup

- `config/LEAGUES.txt` — one nowgoal26 league URL per line, format `/league/<season>/<id>`. **`<season>` takes two forms**, both accepted: `2025-2026` for a cross-year European league (`.../league/2025-2026/36`) and `2025` for a calendar-year one — Scandinavia, Brazil, Japan, MLS, and others that play inside a single year (`.../league/2025/71`). See "Season labels" below.
- `data/` — one gitignored tree, split by provenance: **`data/raw/`** is scraper output only (`<league>_<season>.csv` and `_detail.csv`), **`data/processed/`** is derived (`_enriched.csv`, written by `features/enrich.py`). Both auto-create on write. Both are declared in **`domain/paths.py`**, the only place a data directory or a sibling-file path is constructed — never rebuild one by hand from a filename.
- A locally installed **Chrome** — Selenium 4 auto-manages the driver and runs headless.

## Architecture

### Package layout

Four layers, imported **absolutely** and strictly one-directional — `domain` → `scrapers` → `features` → `modelling`, with `qa` off to the side. Nothing lower may import something higher; that rule is the whole point of the split, so keep it.

| package | holds | may import |
|---|---|---|
| `domain/` | `match.py`, `match_detail.py`, `goal.py`, `event.py` (Pydantic contracts; `match.py` also holds the date and **season-label** parsers), `columns.py` (CSV column order), `paths.py` (where files live, and filename↔league/season), `stats.py` (pure derived-stat kernel), `scope.py` (which historical matches are usable) | nothing internal |
| `scrapers/` | `driver`, `links`, `parsers`, `schedule`, `detail`, `detail_parsers`, `goals`, `live_rows` (the shared live-page row reader), `goal_parsers`, `event_parsers`, `browser_pool`, `csv_io`, `constants` (DOM selectors) | `domain` |
| `features/` | `enrich.py` (the base+detail join), `engine.py` (the as-of-round feature matrix), `chain.py`, `history.py` (which history matches count, and the shared build shape), `goals.py` (goal-timing aggregates), `events.py` (card/substitution aggregates), `ratepair.py` (the shared home/away Poisson pair) | `domain` |
| `modelling/` | `scoreline`, `experiment`, `filter_study` | everything below |
| `qa/` | `report.py`, `universal.py` (dataset-agnostic checks), `league.py`, `detail.py`, `goals.py`, `events.py`, `validate.py` (orchestrator) | `domain` |

Every entry point is a module inside its package, run as `python -m <package>.<module>` from the repo root — there are no top-level scripts. Do **not** use relative (`from .x import`) imports anywhere — Ruff's `TID` rule bans them. Import as `from scrapers.parsers import ...`, `from domain import stats`, `from features import engine`.

Two names moved and are easy to mis-search for: the old `constants.py` split into `scrapers/constants.py` (DOM selectors, user agents, transliteration table) and `domain/columns.py` (`ORDERED_DF_COLUMNS`, `DETAIL_ORDERED_COLUMNS`, `per_match_columns()`); the old `df.py` is `scrapers/csv_io.py` and the old `features.py` is `features/engine.py` (renamed because `features.matrix` would have collided with the pervasive local `matrix` variable). ### Scrape flow

`schedule.scrape_all()` → `links.get_leagues_links()` reads league URLs, `links.parse_league_url()` splits each into `(season, league_id)` → `schedule.scrape_league()` opens headless Chrome (`driver.get_driver()`), renders the page, and iterates rounds `1..current`. For each round it clicks the round span (`driver.click_round`) and syncs the standings dropdown to the same round (`driver.sync_standings_to_round`) — both use `WebDriverWait`, not `sleep`. It parses `driver.page_source` with BeautifulSoup: `parsers.parse_standings()` builds a `{team_id: rank}` map, `parsers.parse_schedulis_row()` extracts each `div.schedulis` match. Teams are matched to standings **by team id** (`toTeam('<id>')`), not by name. Rows are validated by the `Match` model (`schedule._validate`) and written by `scrapers/csv_io.py:save_df_to_csv()` (column order from `domain.columns.ORDERED_DF_COLUMNS`).

Key DOM facts (nowgoal26): only one round renders at a time (`div.round span[round=N]`, live round has class `current on`); each match row carries `@matchid`, `@score`, `span.ht` (half-time), `span.date[data-t]`; standings are at `ul#standingList li.standlis` with a per-round dropdown `li[data-st-r=N]`. All selectors live in `scrapers/constants.py`.

`parsers.parse_schedulis_row()` returns **only scraped primitives** — no derived values. Every derived column (goals splits, results, market flags, date and odds derivations) is a `@computed_field` on `domain/match.py:Match`, computed from `domain/stats.py`. Keep that division: new DOM extraction goes in `scrapers/parsers.py`, new arithmetic on already-scraped values goes on the model or in `domain/stats.py`.

### Detail enrichment (second stage)

`scrapers/detail.py` scrapes each finished match's detail page (`https://live10.nowgoal26.com/match/h2h-<match_id>` — same id as the schedule row) into **one wide feature row** per match. `scrape_match_detail(driver, match_id)` is **mode-agnostic** (a future prediction mode can feed upcoming ids); `enrich_finished(limit)` reads ids from `data/raw/*.csv` and is **resumable** — it skips ids already in `data/raw/<league>_detail.csv` and appends incrementally. It runs a **`ThreadPoolExecutor` of `WORKERS = 4`**, each thread holding its own Chrome for the whole run (a Selenium session is not thread-safe to share); a lock serialises the CSV appends. Detail is ~1 page render **per match** (heavy: ~380/season) — always run it resumable, not from scratch.

The scraper writes **nothing but that detail file**. Joining it back to the base league CSV is `features/enrich.py` (third stage), which left-joins on `match_id` into `data/processed/<league>_enriched.csv` — both raw files untouched. It was moved out of `scrapers/detail.py` on 2026-07-27 because a join is not a scrape; the practical gain is that a stale or deleted enriched file is now rebuilt in seconds without starting Selenium. Anything describing the detail scraper as writing `_enriched.csv` predates that.

`scrapers/detail_parsers.py` parses each section: `parse_odds_1x2` (Bet365-or-first 1X2, initial+live; the 1X2 cells are `td[data-e="1"]`), and the H2H widget tables `tr[id^='tr1_'/'tr2_'/'tr3_']` (v1=home recent, v2=away recent, v3=H2H; score span class is indexed per table so match on prefix `span[class^='fscore']`, and each row is 15 cells — league/date/teams/score/**corner**/1X2 odds). Those rows feed two outputs: **aggregates** (`aggregate_recent`/`aggregate_h2h` → `*_recent_*`, `h2h_*`) and **per-match column blocks** (`flatten_history` → `home_lastN_*`/`away_lastN_*`/`h2h_lastN_*`, last1 = most recent, `N` up to `domain.columns.MATCHES_PER_SECTION`, oriented to the section's subject team). Plus best-effort strength/guess/standings/fixtures. Per-match derived stats (over2.5, BTTS, comeback, 1X2 result, implied prob) live in **`domain/stats.py`**, shared by the `Match` model and the detail records. Aggregate/odds fields are validated by `domain/match_detail.py:MatchDetail`; the per-match blocks are merged in as plain data. Full column order (incl. generated per-match names) comes from `domain.columns.DETAIL_ORDERED_COLUMNS` / `domain.columns.per_match_columns()`.

### Live-page events: goals, cards, substitutions (fourth stage)

`scrapers/goals.py` scrapes each match's **live** page (`https://live10.nowgoal26.com/match/live-<match_id>`) — a *different* page from the h2h detail page, same match id — into the **global** store `data/raw/goals.csv`, one row per goal.

**Goals are identified by the running score, never by the icon.** Measured on live pages 2026-09-22: an open-play goal carries `1.png` (alt "Goal") but a penalty carries `7.png` (alt "Penalty Scored"), so an icon whitelist silently drops every penalty. Chelsea 1-0 Fulham has *zero* rows with the goal icon — its only goal was a penalty at 45+3'. Pogon 0-3 Lech shows the running score jumping 0-1 to 0-3 for the same reason. The running score is strictly better: goal and penalty rows both carry it, VAR rows ("Goal Disallowed", "Goal awarded") never do, and it identifies the scoring side by which number advanced — which also handles own goals without knowing their icon. The icon's `alt` is still stored as `kind`, but is never used to decide whether a row is a goal.

**The store is global, not per league-season.** A fixture's history references cup ties, European games and other leagues, so a referenced match belongs to no single league-season file — and the dedupe that makes the scrape affordable only works across all of them. The key is the nowgoal match id. `domain/paths.py:goals_path()` / `goals_done_path()` own both filenames; this is the one documented exception to the `<league>_<season>_*` naming scheme.

**`data/raw/goals_done.csv` is the resume key, not `goals.csv`.** A 0-0 match produces zero goal rows, so deriving "already scraped" from the goal store would re-fetch every goalless match on every run, forever. The attempt log records one row per *attempted* match with its goal count.

**The work list is the union of the corpus and the history blocks, deduplicated before any fetch.** History rows carry the referenced match's own id and league id in the `index` and `name` attributes (`HIST_MATCH_ID_ATTR` / `HIST_LEAGUE_ID_ATTR`); these are now flattened into `*_lastN_match_id` / `*_lastN_league_id`, which took `DETAIL_ORDERED_COLUMNS` from 501 to 537. **Detail files scraped before 2026-09-22 have neither column**, so `scrapers.goals` finds no history ids until detail is re-scraped. Measured scale: 17.8 references per match, ~14 still new by the twentieth page, 48% already corpus matches.

**Testing the minutes: the half-time score is a free oracle.** `qa/goals.py` reconciles all goals against the stored full-time score *and* goals with `minute <= 45` against the stored half-time score. The second is what tests the minute rather than the count — mishandle stoppage and a 45+3' goal lands in the second half and the check fails loudly on every such match. `minute` and `stoppage` are stored separately for exactly this reason (45 and 3, never 48). History matches from other competitions have no stored score, so only the internal checks apply to them; that asymmetry is reported, not hidden.

**Cards and substitutions ride along on the same render.** `scrapers/goals.py` fills two stores from one page: `data/raw/goals.csv` (`domain/goal.py`) and `data/raw/events.csv` (`domain/event.py`, yellow/red cards and substitutions). Measured on 12 live pages 2026-09-23, the page carries exactly eight event types, and **exactly the three score-carrying ones are goals**: `1.png` Goal, `7.png` Penalty Scored and `8.png` Own Goal, against `3.png` Yellow Card, `2.png` Red Card, `11.png` Substitution and `14.png` VAR, none of which ever carry a running score. That is the running-score rule confirmed rather than assumed.

**The event row is five cells and the minute is the middle one** — `td[0]` home content, `td[1]` home icon, `td[2]` `b.score` minute, `td[3]` away icon, `td[4]` away content. Two things follow, both in `scrapers/live_rows.py`, which both parsers share so they cannot drift: **side comes from which half of the row is populated**, not from where the name falls in the row text (a home event reads "Chukwueze S. 4 - 5 78'", an away one "90+4' Cherki R."); and **the event's icon is the one beside the minute**, not the first `<img>` in the row. Taking the first image names the same substitution "Sub in" on one side and "Substitution" on the other, purely because the content cell precedes the icon cell on one side and follows it on the other — that artefact is what made an early probe report 47 "Sub in" and 43 "Substitution" events. A substitution is **one** row: `11.png` in the icon cell, with `4.png`/`5.png` marking the two players inside the content cell.

Side is not how a goal is attributed — a goal is attributed by which running score advanced, and an **own goal** is exactly the case where the two disagree, since it renders on the scorer's side but credits the opponent.

**Player names are stored for events but not for goals**, and that asymmetry is deliberate. A goal de-duplicates exactly on its running score, which is unique within a match. A card has no such key, and two players on the same side can be booked in the same minute, so collapsing on (minute, side, kind) alone would silently merge them. The names make the de-duplication key exact.

**Two attempt logs, not one.** `goals_done.csv` and `events_done.csv` are separate, which is what let the events store be added to a corpus already fully scraped for goals: such a match is fetched exactly once more, writes only the store it is missing, and is then done for both. `qa/events.py` has **no free oracle** — nothing in the corpus independently counts cards — so it checks structure (ranges, kinds, contiguous index, ordering, at most six substitutions per side) plus wide per-match rate bands, and says so rather than implying the same guarantee `qa/goals.py` gets from the half-time score.


## Domain notes

- Only **finished** matches are emitted — `parsers.parse_schedulis_row()` returns `None` when HT+FT scores don't both parse as `int - int`, so unplayed/live rows are skipped.
- Standings positions are cumulative **as of the round being scraped** (dropdown synced per round).
- **Odds come in three flavours, one pass each.** The schedule odds column is a single three-cell widget (`ROW_ODDS_CELLS`) whose meaning depends on the header selectbox, so `driver.switch_odds_type(driver, kind)` clicks `li[type='...']` and the choice persists across round clicks. `scrapers/constants.py:ODDS_TYPES` maps our name to the DOM type and the header label it must show afterwards: `1x2` → `O` (home/draw/away), `ah` → `L` (home/**line**/away), `ou` → `T` (over/**line**/under). `scrapers/schedule.py` scrapes 1X2 first, then loops the secondary types and switches back. The switch is verified, not assumed — it returns `False` if the header label never changes, and a repaint guard waits for the first row's odds to actually change. Missing odds parse to `None` (`has_odds` / `has_ou_odds` / `has_ah_odds` = False); all odds fields on `Match` are nullable.
- **For AH and O/U the informative column is the line, not the price.** nowgoal moves the handicap/goal line and holds both prices near 1.90, so `ah_line` and `ou_line` carry the signal and `implied_over` / `implied_ah_home` are only the tilt around it. `parse_line()` handles split quarter-lines, where nowgoal hangs one minus sign off whichever half it reaches first so the sign belongs to the whole expression (`0/-0.5` → -0.25, `-1/1.5` → -1.25). **Positive `ah_line` means the home side is favoured and gives the handicap — the opposite sign to football-data.co.uk's `AHh`**, so any comparison against that source has to flip one of them.
- Markets: `is_seven_or_more_goals` (over 6.5), `is_comeback` (HT-loser wins at FT) split into `is_comeback_home`/`is_comeback_away`. Raw score strings (`ht_score`, `ft_score`) are kept alongside the derived goal ints.
- **Position within a round.** `match_index_in_round` is 1..`matches_in_round`, ordered by kickoff datetime then home name then away name (`domain/match.py:round_sort_key`). It is assigned in `scrapers/schedule.py:_order_round` over **every scheduled match in the round including unplayed ones**, then only finished rows are written — so `matches_in_round` can exceed the row count for a partially-played round, and the position cannot be recomputed downstream (unplayed rows never reach the CSV). This is the one derived column that cannot be a `@computed_field` on `Match`, because it depends on the round's other rows.
- **Season labels come in two shapes and are stored verbatim.** `2025-2026` for cross-year leagues, `2025` for calendar-year ones. They are **not** normalised into a common form, because an English 2025-2026 season (Aug–May) and a Norwegian 2025 season (Mar–Nov) are different things and writing `2025-2025` would invent a fact. Consequences, all real bugs that have been fixed but are easy to reintroduce: (a) never slice a season out of a filename by fixed width — use `domain/paths.py:split_league_season`, since a 9-char assumption turns `norway_eliteserien_2025` into `("norway_elites", "rien_2025")`; (b) labels from the two conventions **never compare equal** even when contemporaneous, so `groupby("season")` splits them and an `isin([...])` season list matches neither — use `domain/match.py:season_start_year` when you mean "which seasons overlap in time". Sorting is safe as strings (the start year is a fixed-width prefix).
- **`TRAIN_SEASONS` / `TEST_SEASONS` (`features/engine.py`) are literal labels fixed by `notes/PREREGISTRATION.md` §2, and a calendar-year league can never match them.** That exclusion is correct — the preregistered corpus is closed, and widening it is a protocol amendment, not a code change. `load_enriched` now emits a `UserWarning` naming any league-season in neither split, so a newly scraped league cannot sit in `data/` contributing to nothing unnoticed.
- **Never read `match_index_in_round == 1` as "the first match of the round".** 15.6% of matches share their round's earliest kickoff and the tiebreak between them is alphabetical, i.e. meaningless. Use `features/engine.py:round_position`, which derives tie-aware `earlier` / `later` / `slot` / `slots` from `date`: joint-first is `earlier == 0` (321 matches in the current corpus), joint-last is `later == 0` (263). These are derived, not stored, because they are pure functions of a column that is already there. The three former DOM-order booleans (`is_first_match_in_round`, `is_before_last_match_in_round`, `is_last_match_in_round`) were removed on 2026-07-26 for exactly this reason.

## Conventions

- Work directly on `main`. There is no `dev` or feature-branch flow — `dev` was merged into `main` and retired on 2026-07-26. Since nothing isolates a bad commit from the default branch, run `uv run ruff check && uv run ruff format --check && uv run mypy .` before committing.
- Pin dependency versions exactly in `pyproject.toml` (matches existing style); update `uv.lock` via `uv`.
- Absolute package imports only (`from domain import stats`), never relative — enforced by Ruff `TID`. Respect the layer direction in the table above.
- Never hardcode a data directory or build a CSV's sibling by string surgery (`base_path.replace(".csv", "_enriched.csv")` was the old idiom and silently resolves to the wrong directory now). Go through `domain/paths.py`.
- Only `scrapers/` may write to `data/raw/`. Everything else derives into `data/processed/` and must be reproducible from the raw files — that is what makes the raw corpus safe to treat as ground truth and a derived file safe to delete.
- Older `notes/` entries written before 2026-07-27 cite the earlier flat layout — module paths (`features.py`, `constants.py`, `df.py`, `stats.py`) and the single `data/` directory. Their findings stand; only the paths moved — see the amendment log in `notes/PREREGISTRATION.md`.
